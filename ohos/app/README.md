# NCR app for HarmonyOS

The HarmonyOS application that runs NCR on the phone: it loads a scene baked by Falcor and renders and
trains it frame after frame, the hash grids and all passes on the GPU (Vulkan), the two MLPs on the NPU
(NNRt, HiAI Foundation), and shows the result with a panel like the desktop's. The frames are those of
the runtime in `ohos/replay` (`replay::Runtime`), the same the command-line replayer runs and checks
against Falcor; see `ohos/README.md` for what the runtime does and how it was verified.

## Layout

```
AppScope/app.template.json5       app.json5 is generated from it (the bundle name comes from the signing)
build-profile.template.json5      build-profile.json5 is generated from it (with the signing)
entry/src/main/ets/               ArkTS: EntryAbility (launch arguments, full screen), pages/Index (the XComponent and the panel)
entry/src/main/cpp/app.cpp        native side: NAPI module, XComponent callbacks (surface, touches), render thread,
                                  presentation, assets, the scenes on the phone, the panel's state, log
entry/src/main/cpp/CMakeLists.txt libentry.so = app.cpp + ohos/replay/ncr_runtime.cpp
entry/src/main/resources/rawfile/ generated by tools/sync_assets.py (not in git)
tools/                            build, signing, assets, scenes, deployment, driving the screen
```

## Building and running

From the repository root, in Git Bash, with DevEco Studio installed (its hvigor, node, ohpm and SDK are
used; `DEVECO_HOME` overrides the location) and the phone connected over hdc:

```bash
python ohos/tools/bake_scene.py --all            # Falcor bakes every scene and variant: ohos/_build/scenes/<scene>/<static|anim>
python ohos/npu/export_models.py --only inf_256x256 --only _train_4096 --om    # the NPU models, once
bash ohos/app/tools/native_check.sh              # compiles the native library alone (quick check)
bash ohos/app/tools/build_hap.sh                 # assets -> rawfile, signing -> build-profile.json5, hvigor
bash ohos/app/tools/deploy.sh                    # build, install, start, wait 30 s, log and screenshot
python ohos/app/tools/push_scenes.py             # the baked scenes onto the phone (after the first install)
bash ohos/app/tools/deploy.sh --no-build --args "--scene=cornell-box --variant=anim --save-at=60" --pull-out 60
```

`deploy.sh` leaves the app's log in `ohos/_build/app.log` and a screenshot in
`ohos/_build/app_screenshot.jpeg`; with `--pull-out`, what the app saved in `ohos/_build/app_out`
(`display.bin`, `trained.ckpt`, `schedule.txt`, which `ohos/tools/display_check.py` and
`ohos/tools/train_compare.py` check like the replayer's output).

## Scenes

The scenes are the desktop's: every folder of `media/scenes` with a scene file, in the variants
`run.bat` offers, static (`scene-v4.pyscene`) and anim (`scene-animation.pyscene`). That is nine
scenes and fourteen bakes (teapot has no scene file, on the desktop either). `bake_scene.py` bakes
them; an animated one also gets its track, the scene's data over one loop of its animation, which the
runtime plays back (`ohos/README.md`, "Scenes, animation and the camera").

They do not go into the HAP (60 to 400 MB each): `push_scenes.py` puts them into the app's files
folder, `<files>/scenes/<scene>/<variant>`, and skips what is already there unchanged. The app lists
what it finds there when it starts, or when *Rescan Scenes* is tapped. `sync_assets.py --scene
<scene>/<variant>` can still bundle one into the HAP (`<files>/ncr/scenes`).

## The panel

Over the picture on the right, *Hide UI* / *Show UI* at the top left. What the desktop shows in
Mogwai for this project, as far as the phone has it:

| Section | Controls | Desktop counterpart |
|---|---|---|
| Scene | the scenes, static / anim, *Play Animation*, *Time Scale*, the animation time, *Rescan Scenes* | `run.bat`'s scene and variant, Mogwai's time controls |
| Camera | *Camera Animated*, *Move Speed* (0.25x, 1x, 3x, 10x of the scene's camera speed), the camera's position and direction, *Reset Camera* | `--camera-anim`, Mogwai's camera controls (Ctrl and Shift change the speed by 0.25 and 10) |
| NeuralRadiosity | *Render Mode* (Idle, Render, Train, Online Train), *Save / Load model state*, *Reset model*, *Use NEE*, *RHS Glossy Bounces*, *Diffuse Trains On Glossy*, *Mirror Albedo*, *Env Color Encoding*, *Post Filter*, *FXAA*, the batch sizes | the pass's panel (`NeuralRadiosity::renderUI`) |
| Training Schedule | *Enable*, heat and hold, learning rate and EMA decay now, the events, every schedule setting, *Reset schedule* | the pass's "Training Schedule" group |
| Frame Times | the frame and each recorded segment of it | Mogwai's profiler |

- A switch the bake cannot honour is grey: no animation in a static scene, no NEE switch without lights.
  The desktop's other panel entries change what Falcor compiles (ray counts, the cluster-reuse path)
  and need a new bake.
- *Train* runs only the training part, with the baked shaders (the desktop's Train mode compiles
  ConeTrace for more rays).
- *Save model state* writes `<files>/models/<scene>-<variant>.ckpt`; *Load model state* restarts the
  scene from it, *Reset model* from the bake's fresh model.
- The camera, with two thumbs as on a gamepad, which Falcor's first-person camera also takes: the left
  half of the screen is a stick (it appears where the finger goes down) that moves the camera along
  the view and sideways, at the scene's camera speed at full stick (the desktop's WASD speed, 1 unit
  per second in these scenes, times *Move Speed*); a drag on the right half turns the view, right and
  down as the mouse does on the desktop, half a turn for a drag across the whole screen; ▲ and ▼ at
  the bottom right move it up and down while held. Both thumbs work at once; a finger keeps its role
  until it is lifted. Touching the picture turns the camera path off (on the desktop the camera's
  *Animated* box has to be unticked before WASD moves it). With the panel shown the right half is the
  strip left of it; hidden, the whole right half.
- The touches are read by a layer of the page over the whole screen (`pages/Index.ets`), which passes
  the stick, the up / down buttons and the turns to the native side (`cameraStick`, `cameraLift`,
  `cameraLook`); the render thread moves the camera at the start of each frame by speed times the time
  since the last frame (at most 0.5 s; Falcor clamps at 0.1 s, which at the phone's frame times would
  slow the camera down). The panel and the buttons are children of the page's Stack of their own, so a
  touch on them does not also reach the camera layer.
- The animation follows the clock (*Time Scale* slows it down); `--dt` steps it by a fixed time per frame.

## Launch arguments

One string, `--name=value` or `--flag`, given by `deploy.sh --args` (`aa start ... --ps args " ..."`);
started from the home screen the app has none and uses the defaults.

| Argument | Default | |
|---|---|---|
| `--scene=<name>`, `--variant=static\|anim` | the last scene run, else the first found | a scene on the phone; without `--variant` the static one, else anim |
| `--set=<name>:<value>[,...]` | | settings of the panel and the schedule by name (`ncr_replay --list-settings` lists them), e.g. `--set=cameraAnimated:0,mode:1` |
| `--dt=<seconds>` | the clock | animation time per frame, for runs that must repeat exactly |
| `--networks=npu\|tiles` | `npu` | `tiles` runs the MLPs on the CPU (for comparisons) |
| `--model=bake\|<path>` | `bake` | the model at the start of the baked frame, or a checkpoint |
| `--train-tile=<n>` | 4096 | samples per training graph; the HAP holds the 4,096 graphs (`sync_assets.py --train-tile`) |
| `--no-train`, `--copy-tiles`, `--cpu-prefix-sum` | | as for the replayer |
| `--loss=<n>` | 0 | print the training loss every n frames |
| `--log-every=<n>` | 30 | per-pass times in the log every n frames |
| `--save-at=<frame>` | 0 | after that frame write `display.bin`, `trained.ckpt`, `schedule.txt` to `<files>/out`; with `--save-results` also every image and ray-batch buffer |

## Checking the screen without a hand on the phone

`tools/ui.py` drives the app through the phone's `uitest`: `texts` lists what is on the screen with
its bounds, `tap <text>` taps an element by its text, `toggle <label> [on|off]` sets the switch in that
row, `swipe x1 y1 x2 y2` (on the picture: the camera; on the panel: scrolling), `shot <name>` saves a
screenshot as `ohos/_build/<name>.jpeg`. Coordinates are screen pixels (2848x1320 in landscape).

## Signing

A HAP installs only when it is signed, and HarmonyOS debug signatures are made by DevEco Studio for one
bundle name; they cannot be made from the command line. The signing stays out of git:
`tools/gen_build_profile.py`, run by every build, merges `signing.local.json` into
`build-profile.json5` and takes the bundle name for `AppScope/app.json5` from the signing profile.

- Own signature (the app keeps its own place on the phone): run `bash ohos/app/tools/build_hap.sh` once
  (it generates the project files DevEco needs), open `ohos/app` in DevEco Studio, *File > Project
  Structure > Signing Configs*, tick *Automatically generate signature*. The next build moves what
  DevEco wrote into `signing.local.json`. Bundle name `com.example.ncrgi`.
- Borrowed: `python ohos/app/tools/gen_build_profile.py --from <other project>/build-profile.json5`.
  The app then has that project's bundle name, and the two replace each other on the phone.

## On the phone

- Assets: the HAP carries the runtime's shaders and the NPU models in `rawfile/ncr` (under 1 MB). The
  first start extracts them to the app's files folder (`/data/app/el2/100/base/<bundle>/haps/entry/files/ncr`
  from hdc's shell); a later start only compares the manifest, and a changed one is extracted into an
  emptied folder. The scenes are in `<files>/scenes` (`push_scenes.py`).
- Switching scenes takes the running runtime down (GPU memory, NPU graphs) and loads the next one:
  3 to 4 s for a scene's data, acceleration structures, 12 pipelines and four NPU graphs. The Vulkan
  device and the swapchain stay.
- Log: `<files>/ncr.log`, everything the native side prints; hilog (tag `NCR`) has the same lines but
  drops some.
- The status line on the screen shows the loading steps, then the scene, frame number and time and
  what the frame does (training, rendering), or the error.
- In the background the render thread neither renders nor trains. When the window's surface goes away
  the swapchain is released first; the device, the runtime and what it has learned stay.
